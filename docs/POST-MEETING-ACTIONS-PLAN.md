# Post-meeting actions

Inspected 2026-10-06 before implementation: `main.rs`/Store and completion, `commitments.rs`, `memory.rs`, `connectors.rs`, `calendar.rs`, `useMeetingSession`, finished MeetingDetail, shared API client and Electron fixture/harness.

Current behavior: summaries extract tasks and an email draft; commitments are locally detected/reviewed; Calendar creates Google events after consent (Outlook read-only). Jira exports the entire task list and existing opt-in auto-push can create external tasks at completion. There is no reviewed per-action delivery ledger or email sending integration.

Change: additive local `metadata.postMeetingActions` v1 ledger and an Actions tab. Derive bounded suggestions from current tasks, grounded actionable commitment candidates, and existing email draft; no extra AI calls. Preserve classification, owner, literal date, transcript revision and excerpts. Follow-up/calendar/email/Jira wording chooses a suggested destination, never proves a commitment. Review editable payload, then explicitly confirm. Local task and local email-draft adapters plus existing Calendar/Jira credentials behind a domain provider interface; core processing never calls these adapters. Exclude task connectors from automatic completion exports; preserve opt-in note exports.

Files: new backend actions domain/adapters; narrow changes to main/calendar/connectors; new UI Actions panel; existing session hook/App/workspace/detail prop threading/shared styles; synthetic Rust/HTTP/Electron tests; package test command and root guide. No dependencies or database migration.

Risks: unknown speakers; ungrounded legacy tasks/email drafts; relative dates/time zones; missing or expired permissions; provider timeout after creation; crashes between dispatch/receipt; repeated clicks; concurrent edits/deletion; summary regeneration; old auto-push settings. Require explicit owner, typed start/end and reviewed recipients; never infer emails or resolve relative dates. Record reservation atomically before dispatch and release locks during network work. Persist success/error; retry only definite no-creation errors after fresh confirmation. Ambiguous network/server outcomes and interrupted reservations block redispatch; user checks provider. Historical receipts remain visible after source edits; new execution rejects stale revision. Local drafts are editable saved text, never sent.

Plan: (1) domain suggestion/validation/ledger/tests; (2) single-operation adapters with permission checks and structured safe errors; (3) atomic API orchestration; (4) minimal review UI/loading/empty/errors/history; (5) per-type, persistence, permission/retry/stale/concurrency tests and Electron real interaction; (6) backend/UI checks/build, diff review/fixes.

Acceptance: all action types visible when supported by input; no external calls on detection/completion/tab opening; review required before execution; exact reviewed payload only; every grounded candidate links transcript, legacy provenance limits disclosed; incomplete dates/owners/payload rejected; missing integrations point to existing Settings; repeat confirmation is idempotent and does not resend; uncertain outcomes cannot retry; definite permission/rate-limit rejections allow user-confirmed retry; local task completion and draft/history survive restart/regeneration/source edits; recording/transcription remain unchanged; relevant tests/checks/build pass.

## Implemented boundaries

The Actions API is separate from completion processing; suggestions are derived on read, bounded at 200 items, excerpts at 1,000 characters, and stored history at 500 actions/meeting. Current transcript fingerprints and a lookup index are built once per read. Exact commitment quotes are preserved; legacy task references are context to review, not proof of the task. Generated email drafts may lack turn-level provenance and are labelled for review.

Reviews show the connected Calendar account or Jira site/project/type; adapters verify the public destination fingerprint before dispatch. A disconnected connection produces a permission error; consent/setup stays in existing Settings. Start/end must be explicit and include a timezone; invitees are user-entered. Google invites the reviewed recipients. Jira creates one issue with only its reviewed title/description, configured project/type and existing ADF builder. It does not resolve transcript people to Jira assignees. Payloads follow the [Google event insertion contract](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) and [Jira issue creation contract](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/#api-rest-api-3-issue-post).

Successful confirmations cannot be repurposed into different payloads. Local task/draft changes and receipts are one atomic write; external calls occur after an atomic durable reservation, outside meeting/session locks. A detached attempt survives HTTP disconnection; unresolved reservations after process interruption stay blocked. Provider error bodies/tokens are not exposed. Retry means a new explicit reviewed confirmation following a definite rejection, with no automatic network retries. User must check the provider for uncertain outcomes; automatic reconciliation and remote email drafts/sending are future adapters. Drafts can be reviewed before saving, viewed and copied afterwards; saved confirmed payloads are immutable.

Automatic task exports are intentionally disabled at completion and their Settings toggle shows review required; existing opted-in note exports and explicit manual connector exports remain. No dependencies, capture/transcription changes, cloud infrastructure, Postgres changes or schema migrations were introduced.

Diff review found an existing connector receipt get/put race that could overwrite a concurrent confirmation. Scope was expanded narrowly to atomically mutate only connector receipt metadata, preserving simultaneous notes, tasks and ledger writes and never reviving deleted meetings. The isolated HTTP test exercises concurrent review, note and two rejected exports. Confirmed cards also hide source excerpts when the current suggestion revision differs from the recorded source snapshot.
